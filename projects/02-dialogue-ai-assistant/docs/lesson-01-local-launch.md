# Урок 1. Первый локальный запуск Django-проекта

## Цель урока

На этом этапе мы не подключаем AI-модель. Сначала проверяем фундамент: Python, виртуальное окружение, зависимости, настройки Django, миграции и запуск веб-сервера.

Главный принцип разработки: если базовый слой не запускается стабильно, добавление AI только усложнит поиск ошибок.

## Корпоративный стандарт проекта

Для проекта зафиксирован Python 3.10.

Причины выбора:

- версия широко используется в корпоративных средах;
- хорошо совместима с Django, DRF, Pydantic и AI SDK;
- позволяет воспроизводить одинаковое окружение локально, в CI/CD и Docker;
- снижает риск расхождения между компьютером разработчика и production-сборкой;
- обновление версии Python будет выполняться отдельно и контролируемо.

Важно: стабильность обеспечивается не только номером версии Python, а сочетанием фиксированной версии интерпретатора, зафиксированных зависимостей, тестов, контейнера и CI/CD.

## 1. Перейти в проект

```powershell
cd "G:\1\Developer of AI agents\Developer-of-AI-agents"
git switch feature/2236-pro-dialogue-assistant
cd "projects\02-dialogue-ai-assistant"
```

Команда `git switch` выбирает рабочую ветку. Ветка нужна, чтобы новые изменения не попадали напрямую в `main`.

## 2. Создать виртуальное окружение

```powershell
py -3.10 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Виртуальное окружение изолирует зависимости проекта. Django и библиотеки этого приложения не смешиваются с пакетами других проектов.

Проверка:

```powershell
python --version
where.exe python
```

Ожидаемая версия:

```text
Python 3.10.x
```

Путь к Python должен указывать на папку `.venv`.

## 3. Установить зависимости

```powershell
python -m pip install --upgrade pip
pip install -r requirements.txt
```

`requirements.txt` — декларация внешних библиотек. Исходный код проекта хранится в репозитории, а сторонние библиотеки устанавливаются отдельно.

## 4. Создать локальный файл настроек

```powershell
Copy-Item .env.example .env
```

Файл `.env` содержит локальные параметры и секреты. Он не должен попадать в GitHub.

На первом запуске ключ Gemini можно оставить пустым: мы пока проверяем только Django.

## 5. Проверить конфигурацию

```powershell
python manage.py check
```

Команда загружает настройки, список приложений, URL и модели. Она не запускает сервер, но находит многие ошибки конфигурации.

Ожидаемый результат:

```text
System check identified no issues (0 silenced).
```

## 6. Применить миграции

```powershell
python manage.py migrate
```

Модель Django — это Python-класс. Миграция — инструкция по изменению структуры базы данных.

В нашем проекте создаются таблицы:

- `conversations_conversation` — диалоги;
- `conversations_message` — сообщения;
- `analysis_useranalysis` — результат второй аналитической модели;
- `reports_generatedreport` — метаданные PDF-файла;
- стандартные таблицы Django для пользователей, сессий и административной панели.

Для учебного запуска используется SQLite. Позже мы заменим её на PostgreSQL, не меняя доменные модели.

## 7. Проверить состояние миграций

```powershell
python manage.py showmigrations
```

Знак `[X]` означает, что миграция применена.

Дополнительная проверка:

```powershell
python manage.py makemigrations --check --dry-run
```

Ожидаемый результат:

```text
No changes detected
```

Это означает, что модели и файлы миграций синхронизированы.

## 8. Создать администратора

```powershell
python manage.py createsuperuser
```

Административная панель полезна для просмотра диалогов и результатов без написания отдельного интерфейса разработчика.

## 9. Запустить сервер

```powershell
python manage.py runserver
```

Открыть:

- API: `http://127.0.0.1:8000/api/`;
- администрация: `http://127.0.0.1:8000/admin/`.

`runserver` предназначен только для разработки. В production Django будет работать через отдельный WSGI/ASGI-сервер и reverse proxy.

## Что происходит внутри команды runserver

```text
manage.py
   ↓
DJANGO_SETTINGS_MODULE=config.settings
   ↓
загрузка INSTALLED_APPS
   ↓
загрузка моделей и URL
   ↓
системные проверки
   ↓
локальный HTTP-сервер
```

`manage.py` не содержит бизнес-логику. Это точка входа для административных команд Django.

## Где здесь ООП

Каждая модель наследуется от `django.db.models.Model`:

```python
class Conversation(models.Model):
    ...
```

Наследование даёт модели готовые возможности:

- сохранение через `save()`;
- удаление через `delete()`;
- менеджер запросов `objects`;
- описание полей;
- интеграцию с миграциями и административной панелью.

Мы описываем предметную сущность, а Django предоставляет инфраструктурное поведение.

## Где здесь алгоритмы

Зависимости миграций образуют ориентированный граф:

```text
conversations.0001
      ├── analysis.0001
      └── reports.0001
```

Django выполняет топологическую сортировку графа, чтобы сначала создать таблицу диалогов, а уже затем таблицы с внешними ключами на неё.

## Типовые ошибки

### PowerShell запрещает активацию

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

### Не найден модуль Django

Виртуальное окружение не активировано или зависимости не установлены.

### Ошибка GEMINI_API_KEY

На первом этапе ключ не требуется. В `.env` допустимо оставить:

```env
GEMINI_API_KEY=
```

### Порт 8000 занят

```powershell
python manage.py runserver 8001
```

## Контрольный результат урока

Этап завершён, когда одновременно выполняются условия:

- `python manage.py check` не показывает ошибок;
- `python manage.py migrate` завершён успешно;
- `showmigrations` показывает применённые миграции;
- Django открывается в браузере;
- пользователь понимает разницу между моделью и миграцией.
