# ADR-0001: Базовая архитектура MONGOOSE AI CORE

- Статус: Accepted
- Дата: 2026-08-02

## Контекст

Платформа должна стать основой для множества AI-агентов и каналов связи. Текущее ДЗ 2236 PRO требует веб-диалога, второй аналитической модели и брендированного PDF, но архитектура не должна ограничиваться этим сценарием.

## Решение

Приняты следующие решения.

### 1. Архитектурный стиль

Используем слоистую Clean Architecture с элементами Hexagonal Architecture:

- Presentation;
- Application;
- Domain;
- Ports;
- Infrastructure.

### 2. Django

Django используется как внешний framework для web, ORM, admin и конфигурации. Domain и Application не должны зависеть от Django.

### 3. API-first

Все пользовательские и интеграционные сценарии проектируются как use cases, доступные через API. Web-интерфейс является одним из клиентов API/application layer.

### 4. LLM providers

Все LLM скрыты за портом `LLMProvider`. Gemini является первой реализацией, но не частью бизнес-логики.

### 5. Agents

Все агенты реализуют общий контракт `Agent`. Возможности подключаются композицией через knowledge, memory, tools, policies и LLM.

### 6. Knowledge base

База знаний — обязательный компонент платформы, а не опциональная надстройка. Она развивается отдельным модулем и подключается через `KnowledgeRepository`/`KnowledgeService`.

### 7. Reliability

Долгие и повторяемые операции проектируются как идемпотентные. Для production предусматриваются очередь, retries, circuit breaker, fallback и dead-letter queue.

### 8. Security

Критические действия проходят policy check и при необходимости human confirmation. Вывод LLM сам по себе не является разрешением на действие.

### 9. Structured output

Все значимые структурированные ответы LLM валидируются Pydantic-схемами до сохранения или построения PDF.

### 10. Architecture Decision Records

Все будущие значимые архитектурные решения фиксируются отдельными ADR.

## Последствия

### Положительные

- заменяемость LLM и других внешних сервисов;
- тестируемость use cases без сети и Django;
- возможность подключать новые каналы;
- единые политики безопасности;
- уменьшение связности;
- пригодность для постепенного перехода к PostgreSQL, Redis, Celery и pgvector.

### Отрицательные

- больше файлов и абстракций;
- выше начальная сложность;
- требуется дисциплина зависимостей;
- для маленького ДЗ архитектура выглядит избыточной.

Избыточность принимается осознанно, потому что проект является не разовой работой, а фундаментом курса и будущих агентов.

## Отклонённые варианты

### Вся логика во views.py

Отклонено из-за высокой связности, плохой тестируемости и невозможности повторного использования через Telegram/API.

### Прямой вызов Gemini SDK из сервисов

Отклонено из-за vendor lock-in и сложности тестирования.

### Один Django app для всего проекта

Отклонено из-за роста связности и невозможности независимого развития модулей.

### Микросервисы с первого дня

Отклонено как преждевременное усложнение. Начинаем с модульного монолита и сохраняем чёткие границы для будущего выделения сервисов.
