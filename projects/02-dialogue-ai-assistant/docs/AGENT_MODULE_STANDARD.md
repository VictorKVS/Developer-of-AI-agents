# Стандарт будущего AI-агента MONGOOSE

## 1. Назначение

Этот документ определяет минимальный контракт любого нового агента, который подключается к MONGOOSE AI PLATFORM.

Агент не создаёт собственную инфраструктуру заново. Он использует общее ядро платформы.

## 2. Что агент получает от платформы

Каждый агент может использовать:

- REST API;
- Web UI;
- Telegram, Email и другие каналы;
- авторизацию;
- роли и права;
- карточку клиента;
- историю сообщений;
- память;
- базу знаний и RAG;
- LLM-провайдеры;
- инструменты;
- аудит;
- мониторинг;
- генерацию PDF;
- очереди и фоновые задачи;
- отчётность;
- Top-100 security controls;
- DevSecOps-конвейер.

## 3. Паспорт агента

Для каждого агента создаётся паспорт.

```yaml
code: security_agent
name: Security Agent
version: 0.1.0
owner: security_team
purpose: Анализ обращений и событий ИБ
status: draft
channels:
  - web
  - telegram
roles:
  - OPERATOR
  - SECURITY_ADMIN
knowledge_scopes:
  - organization
  - security
allowed_tools:
  - knowledge_search
  - report_generator
risk_level: high
human_confirmation_required: true
data_categories:
  - client_messages
  - security_events
retention_policy: organization_default
```

## 4. Обязательные поля паспорта

- код;
- название;
- версия;
- владелец;
- назначение;
- разрешённые каналы;
- разрешённые роли;
- область знаний;
- разрешённые инструменты;
- уровень риска;
- необходимость подтверждения человеком;
- категории данных;
- срок хранения;
- правила аудита;
- метрики качества.

## 5. Контракт агента

Минимальный программный контракт:

```python
from typing import Protocol


class Agent(Protocol):
    code: str

    async def can_handle(self, request, context) -> float:
        """Оценить пригодность агента для запроса от 0.0 до 1.0."""

    async def execute(self, request, context):
        """Выполнить задачу и вернуть структурированный AgentResult."""
```

## 7. Правила безопасности

Агент обязан:

- работать только в разрешённом tenant scope;
- проверять роль пользователя;
- использовать только разрешённые инструменты;
- не выполнять критичные действия только по тексту LLM;
- запрашивать подтверждение человека для опасных операций;
- валидировать структурированный результат;
- фиксировать обращения к знаниям и инструментам;
- скрывать секреты и внутренние ошибки;
- учитывать сроки хранения и согласия;
- создавать security event при подозрительной активности.

## 8. Top-100 для агента

Каждый агент проходит минимум следующие группы проверок:

```text
WEB — безопасность пользовательского интерфейса
API — авторизация, валидация и ограничения запросов
DB  — доступ, изоляция и целостность данных
AI  — prompt injection, tool abuse, data leakage, unsafe output
```

Для агента должна быть сформирована матрица применимости контролей.

## 9. Работа с клиентом

Все действия агента должны быть связаны с единой карточкой клиента, если такая связь допустима.

```text
ClientProfile
    ↓
Conversation
    ↓
AgentTask
    ↓
AgentResult
    ↓
Report / Appeal / SecurityEvent
```

Агент не создаёт дублирующий профиль клиента по каждому каналу.

## 10. Работа с обращениями

Если агент обрабатывает сообщение клиента:

```text
IncomingMessage
    ↓
Appeal
    ↓
Assigned Operator
    ↓
Agent Assistance
    ↓
Security Review при необходимости
    ↓
Response
    ↓
Closure
```

Фиксируются автор, время, канал, исполнитель, просмотр, ответ, изменения статуса и итог.

## 11. Работа с OSINT

OSINT-функции разрешаются только агентам с соответствующим паспортом.

Обязательны:

- заявленная цель;
- правовое основание;
- разрешённые источники;
- журнал запросов;
- ссылки на источники;
- разделение фактов и выводов;
- срок хранения;
- контроль доступа;
- ручное подтверждение для чувствительных проверок.

## 12. Метрики агента

Минимальные метрики:

- количество задач;
- успешность;
- среднее время ответа;
- стоимость LLM;
- количество токенов;
- доля ответов с источниками;
- доля эскалаций оператору;
- количество security flags;
- пользовательская оценка;
- процент исправлений оператором;
- ошибки инструментов.

## 13. Тестирование

Каждый агент должен иметь:

- unit tests;
- contract tests;
- integration tests;
- security tests;
- prompt injection tests;
- permission tests;
- tenant isolation tests;
- degraded mode tests;
- audit verification tests.

## 15. Definition of Done

Агент считается подключённым, когда:

- зарегистрирован в Agent Registry;
- имеет паспорт;
- проходит проверку ролей;
- использует общие LLM и Knowledge API;
- пишет аудит;
- имеет тесты;
- отображается в администрировании;
- имеет метрики;
- поддерживает контролируемое отключение;
- не нарушает правила зависимостей платформы.

## 16. Главный принцип

> Будущий агент — это подключаемый бизнес-модуль, а не отдельное приложение. Он наследует возможности и ограничения MONGOOSE AI PLATFORM и расширяет продукт без дублирования инфраструктуры.
